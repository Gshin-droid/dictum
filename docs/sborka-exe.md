# Как Dictum собирается в exe и почему именно так

> **In English:** *How Dictum is packed into an exe, and why that way.* Design
> notes on the build: the five PyInstaller traps that catch anyone packing a
> Python speech-recognition program into a single file, what was chosen and what
> was rejected. Russian only — [main README in English](../README.md).

Разбор решений сборки: что выбрано, что отвергнуто и на какие грабли наступает
всякий, кто пакует Python-программу с распознаванием речи в один файл.

## Зачем вообще собирать

Программа на Python требует от получателя установить Python, создать venv и
выполнить `pip install`. Три непонятных шага — и главная причина не начать
пользоваться вовсе. Собранный exe убирает их полностью: скачал, запустил.

## Модель лежит снаружи, а не внутри exe

Веса весят 216 МБ, и вшить их внутрь технически можно. Но однофайловая сборка
(`--onefile`) при **каждом** запуске распаковывает всё своё содержимое во
временную папку. С моделью внутри старт растянулся бы до десятка секунд, и так
каждый раз. Снаружи распаковываются только библиотеки — старт 1–3 секунды.

Поэтому веса живут в папке `models/` рядом с exe. Папки нет — они туда
скачиваются при первом запуске и больше не качаются никогда.

## Два способа поставки

| | Размер | Первый запуск |
|---|---|---|
| `dictum.exe` | 60 МБ | качает модель, несколько минут |
| `dictum-portable.zip` | 209 МБ | сразу готов, сеть не нужна |

Второй собирается тем же скриптом: exe, уже скачанная модель и `Прочти меня.txt`
в одной папке, сжатые в архив. Он для машины без интернета, с медленным или
платным — и для флешки.

Собираются оба **по умолчанию**, одной командой. Флаг есть у обратного случая —
`--only-exe` пропускает архив, когда идёт отладка и три минуты на сжатие лишние.
Почему именно так, а не наоборот, — ниже, в разделе про расхождение.

Один способ вместо двух не годится: без интернета первый вариант бесполезен, а
209 МБ ради программы «попробовать» скачает не всякий.

## Пути считаются от программы, а не от исходника

Единственное принципиальное изменение в коде ради сборки. Обычно корень проекта
вычисляют от файла с кодом — но внутри exe этого файла не существует.

```python
def _app_dir() -> Path:
    if getattr(sys, "frozen", False):   # признак, который ставит PyInstaller
        return Path(sys.executable).resolve().parent
    return Path(__file__).resolve().parent
```

От `APP_DIR` считаются `models/`, `.env`, `logs/`, `data/dictation/`. Следствие:
папку с программой можно унести на флешке целиком, ничего не сломав.

## Пять ловушек PyInstaller

Каждая найдена только на живом exe. При обычном запуске из исходников ни одна не
воспроизводится — это главное, что стоит знать: **проверять сборку можно только
собранной программой**.

**1. `sys.stdout` в сборке без консоли — не пустой.** Это заглушка, молча
глотающая вывод. Проверка `if sys.stdout is None` оказывается ложной, вывод
уходит в никуда, и первый exe работал, но выглядел мёртвым: ни строчки в журнале.
Проверять надо признак сборки:

```python
if getattr(sys, "frozen", False) or sys.stdout is None:
```

**2. Библиотека спрашивает свой номер версии.** `onnx_asr` при старте читает
собственные метаданные через `importlib.metadata`, а PyInstaller паспорта пакетов
(`.dist-info`) без спроса не кладёт. Падает на первой же строке:
`PackageNotFoundError`. Лечится `--copy-metadata onnx-asr onnxruntime numpy`.

**3. Данные библиотек не находятся сами.** Тридцать служебных моделей
предобработки звука внутри `onnx_asr` и библиотека записи PortAudio внутри
`sounddevice` — это не код, анализатор импортов их не видит. Нужны
`--collect-data onnx_asr`, `--collect-all sounddevice`,
`--collect-binaries onnxruntime`.

**4. Импорт внутри функции невидим.** `voice_window` и `voice_settings`
импортируются не сверху файла, а внутри функций — так задумано, чтобы окно можно
было не грузить в headless-режиме. Статический анализатор такие импорты не
находит: нужны `--hidden-import`.

**5. Работающий exe держит сам себя.** Пересборка падает на «отказано в доступе».
Скрипт сборки сначала останавливает запущенные экземпляры.

## Антивирусы

Программа ставит низкоуровневый перехват клавиатуры — технически то же самое, что
делает клавиатурный шпион. В упакованном неподписанном exe это классический повод
для тревоги, и не потому что кто-то ошибся, а потому что признак настоящий.

Что сделано, чтобы уменьшить шум:

- **сжатие UPX выключено** (`--noupx`): оно почти ничего не экономит, зато само
  по себе служит поводом для срабатывания;
- **лишние библиотеки исключены** — `torch`, `faster_whisper`, `ctranslate2` могли
  бы приехать транзитом через чужие зависимости и утроить размер;
- **у файла есть паспорт** (`--version-file`): имя, версия, автор, лицензия. Exe
  без паспорта выглядит безымянным куском кода — и для человека в проводнике, и
  для эвристики.

Чем это не лечится: подписью кода. Сертификат стоит 200–400 долларов в год, и для
бесплатной программы покупать его смысла нет. Отсюда же SmartScreen при первом
запуске — в README есть, что нажать.

Отдельно про разделы **YARA и Sigma** на странице VirusTotal: это не движки, на
счёт находок они не влияют. YARA-правило опознаёт упаковщик и само оговаривает,
что совпадение не означает вредоносности. Sigma-правила применяются вообще не к
файлу, а к журналу поведения из песочницы: одно ловит загрузку
`vcruntime140.dll` не из системной папки, другое — любое создание исполняемого
файла. И то и другое — прямое следствие `--onefile`: 228 библиотек
распаковываются во временную папку при каждом запуске и грузятся оттуда. Убрать
это можно только переходом на `--onedir`, то есть отказом от единственного файла.
Пометка HIGH относится к приёму, а не к программе.

Проверка выпуска — `release_check.py`: спрашивает VirusTotal об отпечатке
собранного файла и печатает вердикты движков. Загрузка спрятана за отдельный флаг,
потому что файл остаётся у них навсегда. Перед этим он сверяет своё — см.
следующий раздел.

## Чем доказывается, что сборка живая

Не «собралось без ошибок», а:

- `dictum.exe --check` находит микрофон и грузит модель;
- запуск без ключей: в журнале строка «Готов», у часов появился значок;
- диктовка в Блокнот вставляет текст;
- архив распаковывается **в другую папку** и работает оттуда — это проверка, что
  пути считаются от exe, а не зашиты при сборке;
- в журнале распакованной копии стоит «Загружаю из models/», а не «Скачиваю» —
  доказательство, что переносная копия действительно не ходит в сеть.

## Откуда берутся библиотеки внутри exe

Зависимые библиотеки PyInstaller ищет там же, где искала бы их Windows, — а
значит и в `PATH`. Обнаружилось это некрасиво: в выпуске 1.1.2 внутри exe
оказались **47 библиотек рантайма Microsoft из Eclipse Adoptium JDK 17** —
просто потому, что папка `bin` этого JDK стоит в `PATH` раньше `System32`.

Файлы подлинные и подписанные Microsoft, программа с ними работала. Плохо другое:
сборка начала зависеть от постороннего софта на машине. Снеси JDK, собери на
другом компьютере — и в exe уедут другие файлы. Сборка перестала быть
воспроизводимой, а версия рантайма стала случайной.

Лечится двумя вещами:

- **`clean_path()`** — PyInstaller запускается с `PATH` из списка **разрешённого**
  (`System32`, папка Windows, `Wbem`, наше окружение), а не из системного.
  Запрещать чужие пакеты поимённо пришлось бы вечно, а нужных мест всего три.
- **`check_origins()`** — после сборки читает список того, что вошло в exe, и
  отказывается продолжать, если хоть один файл пришёл не из проекта, не из
  Python и не из Windows. Сторож на случай, если поиск однажды снова уползёт:
  без него поломка была бы тихой — exe собран, ошибки нет, внутри чужое.

Проверять надо именно список файлов сборки, а не наличие строки в настройках:
`PATH` — вещь внешняя, и правило про него ничего не гарантирует.

## Импорт не должен ничего делать

`voice_input.py` при импорте перенаправлял вывод в журнал и ставил ловушку
ошибок с модальным окном. Для самой программы это правильно, но импортируют его
ещё сборщик (ради иконки и номера версии) и тесты.

Чем это кончилось: опечатка в `build_exe.py` показала на экране окно «Dictum: не
удалось запуститься» и **заморозила сборку**, ожидая клика, а весь вывод сборки
ушёл в журнал программы вместо консоли. Десять минут потрачены на выяснение,
почему сборка «висит».

Поэтому обе побочные вещи стоят под `if __name__ == "__main__":`. В собранном exe
`voice_input` и есть `__main__`, так что программа ничего не теряет — проверено
на живой сборке: журнал пишется, версия в шапке та самая. Правило общее: **у
модуля, который кто-то может импортировать, при импорте не должно быть побочных
действий** — тем более необратимых или блокирующих.

## Что мешает сборкам разойтись

Раздаваемых файла два, а собран должен быть один exe: `dictum-portable.zip` —
это тот же `dictum.exe` плюс модель рядом. Разойтись они могут молча, и это
однажды случилось: в выпуске 1.1.2 exe был пересобран, а архив остался от 1.1.1.
Отличались только даты файлов, внутри архива всё выглядело одинаково.

Урок общий: **расхождение, которое видно лишь по дате файла, глазами не
ловится**. Значит ловить должен код, и в двух местах — при сборке и перед
публикацией.

**При сборке — умолчание.** Причиной был необязательный флаг `--portable`: без
него собирался только exe, а прежний архив оставался лежать в `dist` как ни в
чём не бывало. Теперь наоборот: без флагов собирается всё, а `--only-exe` — для
отладки, и он **стирает** прежнюю переносную копию. Забывчивость теперь ведёт к
полному комплекту, а урезанную сборку надо потребовать вслух. Плюс после каждой
сборки exe старая копия удаляется в любом случае: расходиться нечему.

**Перед публикацией — отказ.** `release_check.py` до всякой сети проверяет две
вещи и при несовпадении выходит с ошибкой:

- **exe не старше исходников.** Любой из `voice_input.py`, `voice_window.py`,
  `voice_settings.py`, `transcribe.py`, `build_exe.py` изменён позже, чем собран
  exe, — значит раздаём не то, что написали.
- **в архиве тот же exe.** Сверяется контрольная сумма записи внутри zip с
  суммой самого файла; распаковывать архив для этого не нужно.

Про номер версии отдельно спрашивать нечего: он попадает в exe из `APP_VERSION`
при сборке. Exe не старше исходников — значит и версия в нём оттуда же. Спросить
сам exe нельзя: `dictum.exe --version` в оконной сборке печатает в никуда —
ловушка №1 из списка выше, проверено на живом файле.

## Порядок выпуска

Проверено на выпуске 1.1.2. Шаги 5 и 6 забывались чаще прочих.

1. **Поднять `APP_VERSION`** в `voice_input.py`. Версия оттуда попадает и в меню
   программы, и в паспорт exe — править её больше нигде не нужно.
2. **Тесты:** `.venv\Scripts\python.exe -m pytest -q`.
3. **Сборка:** `.venv\Scripts\python.exe build_exe.py` — без флагов, собираются
   и exe, и архив. Минут пять.
4. **Проверить живьём** — список в разделе «Чем доказывается, что сборка живая».
   Мало «собралось без ошибок».
5. **Проверка выпуска:** `.venv\Scripts\python.exe release_check.py dist\dictum.exe --upload`.
   Отказ — не выпускать, а пересобирать. Из вывода взять отпечаток SHA256 и
   число находок.
6. **Вписать их в оба README** — `README.md` и `README.ru.md`, раздел «Проверка
   антивирусами»: ссылка на отчёт, отпечаток, номер выпуска. Отпечаток от
   прошлого выпуска хуже, чем никакого: README велит не запускать файл, если не
   сошлось, — и у человека гарантированно не сойдётся.
7. **Коммит, тег, отправка:**

   ```powershell
   git commit -am "..."
   git tag -a v1.1.2 -m "Dictum 1.1.2"
   git push origin main; git push origin v1.1.2
   ```

8. **Релиз:** `gh release create v1.1.2 dist\dictum.exe dist\dictum-portable.zip`
   с заметками на двух языках — английский сверху, русский снизу, как в
   предыдущих выпусках.
9. **Сверить размеры** файлов в релизе с локальными: `gh release view v1.1.2
   --json assets`. Это доказательство, что залилось именно то и целиком.
